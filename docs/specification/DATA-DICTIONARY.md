## Conventions and policy boundary

SQL names below use snake_case; HTTP/service objects use camelCase. TEXT dates are text, not an SQL date type. Domain timestamps are normally ISO strings; authentication timestamps use **Unix epoch milliseconds**. UUIDs, timestamps and ownership generated by services are not SQL defaults. `none` means no database default, not an empty-string or null default. Nullable columns may store SQL NULL. Every primary key here is explicitly nonnull in the applied migration.

Constraints listed in field tables are **database-enforced definitions**. FKs default to NO ACTION on update/delete; they enforce referenced-row existence when foreign-key enforcement is enabled, not matching school, role, approval or enrolment. Composite uniqueness/indexes are whole tuples, not unique individual members. SQLite TEXT/INTEGER affinity alone is not strict type checking; only the listed CHECKs explicitly enforce type/range where present.

Sensitivity labels are engineering handling descriptions, not an approved legal classification. School privacy/data owners must approve access, exports, corrections, retention and deletion for real records. **Retention for all business records, logs/backups and evidence remains pending.** Authentication validity is implemented (eight-hour sessions, five-minute transactions, ten-minute login buckets); expiration and opportunistic cleanup are not a complete retention/cleanup SLA.

## Database constraints and service-only rules

- `users.email`, `students.admission_number` and `courses.code` are globally unique; they are not school-scoped unique keys. OIDC `(identity_issuer, identity_subject)` and nullable `students.user_id` are unique. SQLite nullable unique keys allow multiple null values. Guardian `user_id` has no retroactive unique index; migration 0008 rejects new/changed duplicate bindings while preserving existing legacy rows.
- `student_guardians` has **no `id` column**: `(student_id, guardian_id)` is its composite primary key. The database default of `is_primary` is 0; current linking service does not implement a primary-contact selection workflow.
- Attendance has unique `(class_id, student_id, date)`. **Enrolments lack unique `(student_id,class_id)` and assessment results lack unique `(assessment_id,student_id)`**. Migration 0009 adds nonunique pair lookups and INSERT/changed-pair duplicate guards, preserving existing duplicates. An ambiguous duplicate result pair blocks a whole batch; there is no migration cleanup; reviewed result receipts record only explicit new reviews, not a general legacy correction log. Reports lack unique student/term keys.
- Same-school relationships, role eligibility, active teacher/student membership, draft privacy, allowed status enums in legacy tables, legacy score ranges and academic date meaning are service rules. Legacy date schemas frequently require nonempty text only; do not infer calendar correctness.
- Reading CHECKs enforce integer milliseconds/counts and fixed source/provenance. Its service additionally enforces valid nonfuture UTC reading date, language/reference limits, staff scope and retry semantics.
- Resource CHECKs enforce positive integer versions, resource type and paired approval nullability. The unique resource/version key arbitrates stale concurrent revisions; unique version/class protects assignment retries. Content bounds, version/resource consistency, approval eligibility and active student class visibility are service rules. Only approval metadata changes in-place; content versions/assignments are append-only through implemented APIs, not database immutable-row triggers.
- `attendance.recorded_by` is TEXT without an FK. Newer reading/resource actor references have user FKs. User/guardian/student relationship backfill is not performed by migration 0001.

- New administration, curriculum and submission CHECK/unique keys enforce local row shape and revision uniqueness; same-school, live role, review and exact-version authority remain guarded service predicates. Identity status/session/evidence changes and curriculum resource-copy/provenance use atomic D1 batches.
- Reading corrections, profile-link events, submission-window reviews, import items/receipts, report publication receipts and reviewed attendance and assessment receipts/entries block UPDATE/DELETE with immutable-row triggers. Import draft originals and terminal decisions are guarded; a confirmation trigger inserts all checks and receipts in one atomic UPDATE. Other domain histories remain append-only through their APIs; no platform-wide immutable audit is inferred.


- Staged import rows are not reading observations. A confirmed receipt uniquely consumes `(school_id, source_label, external_reference)`; a conflict rolls back the entire confirmation and leaves the draft staged. User-declared source labels/references are not verified vendor identities.
- `assignment_submission_windows` is separate from `resource_assignments.due_date`. No window row means unrestricted; latest closed/elapsed policy denies new attempts using the database clock, while authorized committed UUID replay and feedback remain available.

- Migration 0012 creates no receipts for historical published reports and changes no historical notices. A new receipt atomically publishes exactly one draft and derives DISTINCT eligible guardian login recipients at commit; failure rolls back receipt, report and all notices. The receipt has no public API/export. Report content and notice history do not acquire platform-wide DB immutability or a new retention policy.

- Reviewed registry receipt creation guards the original administrator/current school and validated original snapshot; a trigger inserts its unlinked profile atomically. The receipt profile_id intentionally has no FK to the current profile, while school_id/created_by do. Receipt UPDATE/DELETE is blocked. Canonical request hashing/exact original-session enforcement remain service/SQL predicates, not inferred from text affinity.
- Demo installation marker has no immediate school FK because the pristine seed claim precedes school insert in one atomic batch. Runtime UUID/configuration and winning nonce are service rules; marker rows are not a general immutable audit or credentials. Every normal domain school/account/profile FK remains.
