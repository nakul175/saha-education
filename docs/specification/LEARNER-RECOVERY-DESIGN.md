## Problem and unchanged server guarantees

The earlier assignment editor could retain an uncertain original text while Refresh changed its expected attempt/revision. A subsequent save generated a new UUID, appending an old response or duplicate reviewed feedback as a new latest record. The window editor could similarly reapply a previously committed close after another review reopened responses. Known denied reloads could leave old learner material, feedback and writable controls visible. These diagnosed unsafe outcomes are reproduction evidence, not passing acceptance cases.

The [submission service](../../lib/education/submissions.ts) already replays the exact original authenticated UUID/content/expected number without appending, under current authorization. [Submission windows](../../lib/education/submission-windows.ts) return the original review alongside the current window, without undoing later policies. Closure gates only new attempts; prior committed authorized UUID replay and reviewed feedback remain possible. This slice changes client recovery and displayed privacy. Existing backend authority, CAS, origin/body limits, source records and history remain authoritative and unchanged. Grade, attachment, late penalty, guardian publication, real provider and retention policy are not introduced.

## Pending request and receipt contract

| Operation | Immutable pending request | Acknowledgement |
|---|---|---|
| Learner response | Original endpoint, actor ID and serialized `{response,expectedAttempt,clientSubmissionId}` | Exact original attempt identified by its UUID, attempt number, actor and response |
| Formative feedback | Exact original submission endpoint, actor ID and serialized `{feedback,reviewed:true,expectedRevision,clientFeedbackId}` | Exact original feedback for that attempt/revision/reviewer/text |
| Reviewed window | Original endpoint, actor ID and serialized `{state,closesAt,reason,reviewConfirmed:true,expectedRevision,clientPolicyId}` | Original review plus independently current window |

At the first valid save the client generates one UUID and freezes the complete POST body. While the outcome remains unresolved, draft fields, attempt selection and new-save controls are locked. Refresh may replace current authorized evidence; it must never mutate/rebase that original body. The explicit actions are **Retry pending response**, **Retry pending feedback** and **Retry pending window review**. Each sends the original bytes under the original current actor and endpoint. Repeated lost delivery, malformed or wrong-shape 2xx, network failure or 5xx retains the request. A success status alone does not validate a receipt.

An explicit 400 rejects the request without committing and releases it for correction. An explicit 409 rejects it into required current reload/comparison and explicit review before a new UUID. Known 401/403/404 hides protected views and retains any unresolved request; recovery requires a fresh authorized same-actor reload. A valid original acknowledgement resolves pending state. A later failed refresh is separately labelled: a known saved outcome stays saved, while unavailable current evidence is hidden. No response body is left unread, including non-success responses.

These requests live only in page memory. This is not a persisted outbox: closing the page, full navigation, browser restart or deliberate new session can lose local retry state. Pending 401 offers sign-in in another tab so the page can retain its request. The UI does not claim cross-page automatic deduplication without that original UUID. Current server scope remains the final authority even after a successful client reload.

## Known access loss and current evidence

The [assignment page](../../app/assignments/[id]/page.tsx) resolves current session, approved assignment, attempts/feedback and submission window before displaying an authorized view. A known 401/403/404 on initial read, refresh, mutation or follow-up read clears material, attempts, pupil labels and visible policy/history, and disables protected actions. Another otherwise authorized account cannot recover a request created by a different actor. Original requests may remain private in memory while their evidence/form text is hidden; same-actor current authorization must be restored before retry.

The [window component](../../components/assignment-submission-window.tsx) accepts `actorId`, `available` and `onAccessLost` from its parent. Its mounted lifetime persists after an initially authorized read so `available:false` can hide protected policy/history/reason without discarding a pending request. A successful current-policy GET followed by history 401/403/404 invalidates the partial private view and signals the parent. Non-access history 5xx is a history error rather than an invented revocation: the valid current policy/save acknowledgement remains separately truthful. Scope/generation/mounted guards ignore obsolete history and timer responses.

The [learning list](../../app/learning/page.tsx) re-resolves the session on every initial/reload flow, then reads the current approved assignment feed. It clears old role/cards/class labels when beginning a new load and on a failed/unavailable feed. Guardian access does not show learner actions. Generation and AbortController guards prevent older approved responses from restoring material after a newer denied/current load. A temporary optional class-label failure may leave the accepted feed visible with fallback labels; a known class-label access denial clears the protected feed. All navigation uses native full-page anchors.

These safeguards react to observed responses. Previously delivered content cannot be remotely retracted; authorization can change after a successful read. v2.9 private verified-object evidence now revalidates the original token/expiry/exact identity at actual SQL execution; the public Principal remains compact. Trusted internal service compatibility and already-delivered-content limits remain explicit. This client slice adds no new historical entitlement and makes no production-ready, provider or business-acceptance claim.

## Evidence layers and designed procedures

The [independent contract](../../tests/integration/learner-recovery-ui-contract.mjs) creates fresh synthetic databases with all final migrations, real opaque sessions and actual route handlers using the production Drizzle D1 adapter over SQLite. Lost acknowledgement is injected after an actual committed route response is drained; later attempts/policies and current denial use actual routes/data changes. Unchanged client sources are transpiled, but React hooks/elements/native event values are substituted. This proves callback-state/request behavior under those substitutions, not mounted React rendering, hydration, browser navigation, visual/accessibility or educator acceptance.

The separately invoked [local browser recovery procedure](../../tests/worker-learner-recovery-ui-check.mjs) targets a freshly built disposable Worker and synthetic sessions. [Accessibility sampling](../../tests/worker-accessibility-check.mjs), offline prototype review and UAT remain distinct layers. Related source/suite links do not change any TC outcome. Root-maintained dated execution/publication records contain actual counts/source/environment; this design contains no invented runs.

The existing [reviewed attendance recorder](../../app/classes/[id]/attendance/page.tsx) receives the same narrow current-snapshot/history-denial display correction. History 401/403/404 hides protected rows/notes/reason/history/receipt and blocks actions; restored current reload is required. Temporary history 503 remains an explicit history error beside valid current records. Its backend/date/legacy replacement semantics remain unchanged; TC-203 carries the supplementary designed procedure. The independent suite includes this callback edge under the same substituted-hook scope, while the existing recorder browser procedure remains separate.
