## Current scope and read contract

[Student Registry](../../app/students/page.tsx) and [Guardian Registry](../../app/guardians/page.tsx) retain the existing session, list and create APIs. No table, field, route, handler, educational policy, login binding or backend idempotency capability is added. Current inventory remains 39 tables/325 fields and 56 route files/91 handlers. New profiles start without a sign-in account; [reviewed profile links](../../app/admin/profile-links/page.tsx) remains the separate administrator binding workflow.

Each reload clears old rows, principal, search and comparison authorization, then reads session → authorized list → session. It compares exact actor ID/role/school and accepts only the latest mounted generation. Abort/generation guards discard superseded responses even if a transport ignores cancellation. A missing/disabled/changed account, failed list or mismatched final session cannot restore earlier administrator records or create controls. The server's live SQL authorization remains final; separate session/list/session requests are not a transaction or continuing-session proof after the last response.

Student View uses a native full-page link to the existing student profile route. A reproduced client-transition failure motivated this narrow navigation change; diagnostic failure is not passing browser credit. Student search filters current loaded names and admission numbers locally. The query is limited to 200 UTF-16 code units; at most the first 200 matching profiles are displayed. Shown, matching and loaded authorized counts are distinct, so a later loaded profile can still be found by search. This does not claim server search, total school population or a new database pagination contract. Guardian listing retains its existing scope without inventing a student-style cap. Its scrollable table wrapper is a keyboard-focusable region labelled Guardian profiles. This focused accessibility behavior does not claim certification; final mounted samples and named acceptance remain separate.

## Create and acknowledgement states

Administrator forms verify the current session again before sending a create. A different actor ID/role/school sends no POST, clears the protected view and requires reload. A synchronous ref lock prevents two same-frame submissions. These are client controls; existing backend validation, admission uniqueness, guardian duplicate semantics and legacy birth-date handling remain unchanged.

A known save requires HTTP 201 with a correlated nonempty ID, current school and submitted profile values. The saved acknowledgement remains distinct from a failed subsequent list refresh. It does not become an alleged failed write or cause an automatic second POST.

After any uncertain sent POST—including network loss, 5xx, malformed JSON, mismatched success shape, 401/403/404—both pages abort/invalidate earlier loads and clear all old rows, principal and current create authorization. Submitted values and original actor scope remain private in page memory; creation forms stay hidden and another POST is blocked. A definitive 400 releases the rejected draft for correction. An uncertain create has no UUID receipt, durable retry, automated reconciliation or safe replay guarantee.

The user explicitly chooses Reload students/guardians. Only a fresh authorized load matching the original actor ID/role/school exposes submitted comparison identifiers and the comparison checkbox. A different administrator or family account cannot see or release the pending draft. Finish comparison and start a new draft clears the reminder, resets blank fields and sends no request. It is a human comparison decision, not proof of uniqueness or non-commit. Deliberately creating again may still duplicate a guardian. Navigating away, hard reload or tab loss discards this memory; operational guidance must make that limit visible.
